# Tech Stack Selection: Building the AgentHood from Scratch

To build a state-of-the-art AI Operating System from scratch (inspired by OpenClaw and open-swe), we must choose the right tools for the job. Our system must be extremely fast, never crash, handle long-running background tasks, and be easily deployable anywhere via Docker.

Here is the technical investigation and selection of the programming languages and infrastructure for our V1 build.

## 1. The Core Orchestrator (The Supervisor API)
**Language Choice: Go (Golang)**
*   **Why Go?**
    *   **Concurrency:** Go's `goroutines` are the absolute best tool in the world for handling thousands of simultaneous connections (Telegram webhooks, WhatsApp WebSockets, HTTP requests) without using excessive RAM.
    *   **Simplicity:** Unlike Rust, Go is incredibly fast to prototype in. Unlike Node.js (OpenClaw's current stack), it compiles to a single, statically-linked binary. No `node_modules`. No runtime dependency hell.
    *   **Ecosystem:** Go has massive, battle-tested libraries for building API gateways, connecting to databases, and handling WebSockets.
*   **Role:** The Go server will act as **The Receptionist**. It will receive user messages, parse intent using a fast LLM call, write the task to the database, and immediately reply to the user. It will *not* execute code or run long thought loops.

## 2. The Worker Agents (The Brains)
**Language Choice: Python**
*   **Why Python?**
    *   **The AI Ecosystem:** Python is the undisputed king of AI. `LangGraph`, `Pydantic` (for structured outputs), `tiktoken` (for token counting), and every major LLM SDK are built primarily for Python.
    *   **Flexibility:** We will build the actual "Thinking -> Acting -> Observing" loop in Python.
*   **Role:** We will build a pool of Python "Worker Daemons". These daemons will constantly poll the database for new tasks assigned by the Go Receptionist. When they get a task, they run the LangGraph state machine.

## 3. The Execution Sandbox (The Hands)
**Infrastructure Choice: Daytona (or custom Docker SDK via Go/Python)**
*   **Why Not Local Execution?** As seen in `open-swe`, executing arbitrary bash commands generated by an LLM on the host machine is a catastrophic security risk.
*   **Role:** When the Python Worker Agent decides it needs to run `npm install`, it makes an API call to Daytona (or our own internal Docker engine). The command runs inside an isolated, ephemeral Ubuntu container. The output is streamed back to the Python agent.

## 4. The Source of Truth (The Database)
**Database Choice: PostgreSQL (with pgvector)**
*   **Why PostgreSQL?**
    *   **State Machine Checkpointing:** If the Python agent crashes on step 4 of a 10-step plan, we need to know exactly what Step 3 was. We store every single LangGraph state transition in Postgres.
    *   **The Task Registry:** The Go Receptionist reads from Postgres to tell the user: *"The coding team is currently 40% done."*
    *   **Vector Search:** Using the `pgvector` extension, we can store embeddings of the user's past conversations and codebase files in the exact same database. We don't need a complex secondary database like Pinecone or Milvus.

## 5. Containerization (Docker)
**Everything Must Be Dockerized**
*   To ensure *"what works on your VM works on mine"*, the entire system will be defined in a single `docker-compose.yml` file.
*   `docker-compose up` will spin up:
    1.  The Go API Gateway (The Receptionist).
    2.  The Python Worker Pool (The Swarm).
    3.  The PostgreSQL Database.
    4.  (Optional) A local Docker daemon or Daytona instance for the sandboxes.

## Summary of the Tech Stack
1.  **Go:** The ultra-fast, concurrent API Gateway and Receptionist.
2.  **Python:** The deep-reasoning, LangGraph-powered Worker Agents.
3.  **PostgreSQL:** The resilient, centralized state machine and vector store.
4.  **Docker:** The universal deployment and execution environment.
